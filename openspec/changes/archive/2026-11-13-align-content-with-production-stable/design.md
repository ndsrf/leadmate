# Design

## Context

- The baseline is `src/shell/content/baseline.generated.ts`, a committed file generated by `scripts/gen-baseline.mjs` from `content/stable`. Only `content:promote` runs it. `npm start` builds beta only, and the EAS build runs `sim:embed` only.
- `parity.test.ts` already asserts that the resolved baseline equals `content/stable` on disk, but only when tests are run.
- The updater (`updater.ts`) diffs the remote manifest against the *active downloaded pack* only. With no active pack, `activeFiles` is empty, so everything is downloaded, one file at a time, in a serial loop.
- The baseline holds the parsed pack (text and structure); it holds no image bytes and no file hashes. Images exist only remotely and are fetched on demand through `MediaResolver` once a pack manifest is active.
- The channel default is hard-coded in `channelSetting.ts` and `runtime.ts` (`isDev ? 'beta' : 'stable'`).
- The published stable pointer and the baseline were both v1 at the time of writing, so a stable first install already downloads nothing. The slowness seen was a dev build following beta (v4, no baseline).

## Goals / Non-Goals

**Goals:**
- A dev build behaves like production unless the developer picks Beta.
- A release cannot ship with a baseline older or newer than published stable without failing a check.
- Any download that is still required is faster, without changing the manifest or its format.

**Non-Goals:**
- Zip bundles or any manifest/`formatVersion` change (revisit with measurements after this change).
- Changing which media is fetched per World, or the pointer caching rules.
- Seeding beta from the baseline: the baseline is stable content, and beta differs.

## Decisions

### 1. Dev defaults to stable by removing the `isDev` branch
Make `defaultContentChannel` and the `runtime.ts` channel fallback return stable in every build. Keep the dev-only immediate activation, but only while Beta is selected; Stable in dev activates at next launch, like production.
- *Alternative*: add an env flag to choose the dev default. Rejected: more configuration for a rarely different outcome, and it recreates the production-parity gap.
- Consequence: authors select Beta once in Settings (the control is always shown in dev) and the choice is remembered. `content:watch` keeps building beta.
- A dev device that never stored a choice (and so followed Beta by the old default) moves to Stable on its next launch. Nothing is stored, so no migration is needed.

### 2. Baseline hashes live in a separate generated index
`gen-baseline.mjs` also emits `baseline.hashes.generated.ts`, a map of relative path to sha256 for the files the baseline holds, computed with the same hashing the build uses. The pack object stays unchanged.
- *Alternative*: embed hashes in the pack object. Rejected: it changes the type the validator and parity test use and enlarges the object everything resolves from.
- The updater, with no active pointer on stable, treats the index as the stored copy: a file with an identical hash is not downloaded. Files the baseline does not hold (images) are downloaded.
- **Merged active content (settled).** The baseline holds no bytes and is not serialised back to disk. The first-install pack is staged with downloaded files only, and the active content is the installed pack's files with the baseline filling any file the installed pack lacks. "Complete set" therefore means complete once merged with the baseline.
- Validation before activation runs on the merged result, so a partial pack valid only on its own cannot be activated. If the merge fails validation, the previous content stays active.
- Later updates diff against the merged hashes (the installed manifest plus the baseline index for files the pack lacks), and every pack staged after the first is a complete set copied from the installed pack and the baseline, so partial packs never chain.

### 3. Bounded concurrency in the download loop
Replace the serial `for` loop with a small worker pool (limit 6). Order of *starting* requests keeps the existing priority (structure and text, current World media, next World media, rest). On any failure, stop starting new requests, cancel in-flight ones where the platform allows (their results are never staged either way), and discard staging. Progress counts finished files and is monotonic.
- *Alternative*: unbounded `Promise.all`. Rejected: floods a mobile radio and the host, and makes failure handling harder.
- The limit is a single constant so it can be tuned from measurements.

### 4. Regenerate the baseline at release build time
A single script, `release:prepare`, runs `sim:embed`, then `gen-baseline`, then `content:release-check`, and aborts on the first failure. `eas-build-post-install` and local release builds both call it, so the order cannot drift. `content:promote` keeps calling `gen-baseline`.
- *Alternative*: keep it committed and rely on the parity test. Rejected: the test is not part of the EAS build, and a regenerated file that is committed can still lag.

### 5. Release check compares to the published stable pack
A new script (`content:release-check`) fetches the stable `latest.json` and manifest and compares content version and per-file hashes with the baseline index, for text and structure files only (the baseline holds no images). It compares against the published pointer only; the "older" and "newer" messages already say which side moved. It exits non-zero with the messages in the spec, and fails (not passes) when the host is unreachable. An explicit `--allow-offline` flag skips the unreachable-host failure, prints a warning, and is never passed by the EAS build. It runs inside `release:prepare`, after baseline regeneration.
- *Alternative*: compare only versions. Rejected: same version with different content is exactly the silent drift found between the stable folder and its published v1.

## Risks / Trade-offs

- [Release check blocks a release when offline or the host is down] → Intentional failure with a clear message; the explicit `--allow-offline` override warns loudly and is never the default.
- [Concurrency exposes a race in the shared staging folder] → Downloads for one pack already run one update at a time through the queue; concurrency is only inside a single pack's staging, writing distinct paths.
- [Dev builds on stable can hide beta authoring problems] → Beta stays one tap away; the Beta indicator remains.
- [Baseline hash index grows the bundle slightly] → About one hex digest per text/structure file (around 280 entries); negligible next to the existing generated pack.
- [Seeding from the baseline relies on baseline content matching published files] → The release check enforces equal hashes at release; the merged active content is validated before activation, and a failure keeps the previous content.
- [Merged view adds a second source to the resolver and store] → Only the first install is partial; every later pack is staged complete.

## Migration Plan

1. Ship the code changes. No manifest or `formatVersion` change, so existing apps and published packs are unaffected.
2. Publish stable at the current `contentVersion` only after confirming it matches `content/stable` (bump the version if the folder changed since v1).
3. Run `release:prepare` (regenerate the baseline, then the release check), then build.
4. Rollback: revert the app change; nothing published needs to change.
