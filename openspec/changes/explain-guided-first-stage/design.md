# Design

## Context

The guided first Stage already has Coach marks (`coach-move`, `coach-mark`) and one-shot Hints keyed by `StageSignal` in `src/shell/onboarding/hints.ts` (`first-taut`, `first-fixation`, `leash-limit`, `dog-approaching`), recorded in `seenHints`. Feedback Messages carry `firstTime` (their full-text Hint) and are recorded as `feedback:<kind>`. `StageScene` emits signals once per Stage through `createSignalGate`. The HUD draws the Feedback Message icon, flying meter points, Stage meters, Mark and Jackpot badges, and (from `telegraph-marker-timing`) the Approach ring. The Primer is shown before the simulation. See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**
- A single list of everything the Stage can show, with its explanation, so nothing is missed now or when a sign is added later.
- Reuse the Hint mechanism; add signals, not a new system.

**Non-Goals:**
- The Taste Stage, the simulation, the payload, other Stages' coaching, and the "Cómo se juega" lessons.
- Interactive tutorial steps or blocking overlays.

## Decisions

### 1. One list of signs, coverage by test
`src/shell/onboarding/stageSigns.ts` lists each sign (id, where it is drawn, `hint?: HintId`, `overview?: TextKey`). A test imports the bundle's atlas frame names and Feedback kinds used in the guided first Stage and fails on any that is not listed, and on any entry with neither `hint` nor `overview`. Alternative: rely on review; rejected because new signs would drift out again.

### 2. New StageSignals for the first draw of each sign
`StageScene` emits a new signal the first time a sign is drawn (for example `dog-noticed`, `first-meter`), through the same gate, using the existing `stage-signal` message. Feedback icons reuse `firstTime`. The shell maps each signal to a Hint in `HINT_FOR_SIGNAL`. No simulation change, since signals come from events the scene already reads.

### 3. A Hint queue in the shell
The shell shows one Hint at a time. A due Hint waits in a short queue in a fixed priority (first Fixation, then approaching dog, then the rest), is dropped if the signal reports its sign gone, and pauses with the Stage. Alternative: let Hints overlap; rejected because the first Fixation already stacks the rhythm Hint with a Coach mark and the warning.

### 4. Overview as a Primer card
The overview is one more card in the existing Primer, with a capture taken by the existing capture script (annotated, regenerable) and its labels in the catalog. It runs before the simulation, so reading costs no Stage time. Alternative: a separate briefing screen; rejected because it would add a step to the funnel for content that fits a card.

### 5. Respect Introduced kinds
Signs of an action kind that is not Introduced in the first Stage are not drawn, so they are not listed or explained until Introduced (`introduce-walk-feedback-gradually`).

### 6. Dog signs are drawn by the scene, so they get their own signals
The Dog signs (Fixation "!", Alert circle, eye and gaze line, bark arcs, scent dots, Sintonía glow) are drawn straight in `StageScene.draw`, not through Feedback Messages. Each gets a first-draw signal (`dog-sign` with a `sign` id) through the signal gate. Only signs reachable in the guided first scenario need an explanation, found by a sim test over seeds 1 to 8; the rest are listed as exempt in `stageSigns.ts`.

### 7. One merged Hint at the first Fixation
In the guided first Stage the first Fixation shows one Hint that explains the "!" and the ring together and ends with the Marker instruction. It replaces the rhythm Hint's wording there (the rhythm Hint stays elsewhere) and is recorded as `marker-rhythm` and `marker` plus the sign. The approaching-dog warning waits in the queue. Hints never pause the simulation and stay on screen at least about 4 seconds.

### 8. Capture at the first Fixation, text shared with the lesson
The overview capture is scripted: the existing capture script runs the guided scenario with a fixed seed to the first Fixation, so the "!", the ring, the leash and the controls show together, and annotates it. The walking How-to-play Lesson's "Las señales del perro" control reuses the same capture and the same catalog text, so the Hints, the card and the lesson cannot drift apart. Alternative: hand-made art; rejected because the Lesson art spec requires captures that regenerate from one script.

## Risks / Trade-offs

- [Too many Hints in a 25-second walk] → The queue shows one at a time and drops stale ones. Signs with an overview line and a small effect can skip their Hint. The inventory decides, and the playtest checks the total.
- [The overview card is a wall of labels] → At most about six labels, with the rest left to Hints.
- [Capture drifts from the real screen] → It is regenerated by the script, as for the lesson captures.
- [Overlap with the rhythm Hint] → It keeps priority in the queue.

## Migration Plan

Existing Dogs keep their `seenHints`, and nothing is pushed to Dogs that already finished the first Stage. A Dog that has already played the first Stage sees the new Hints only on a replay or after a progress reset. No record version bump.

## Open Questions

- Which signs get both an overview line and a Hint, and which get one, is decided in the inventory (task 1.1) and checked in playtest.
